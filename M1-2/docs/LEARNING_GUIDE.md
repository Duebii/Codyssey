이 문서는 구현한 기능을 본인의 말로 설명하기 위한 자료입니다. 아래 예시를 읽고 접은 답변을 보지 않은 채 설명해 보세요. 설명 자료의 완성과 학습자 본인의 이해 확인은 구분합니다.

## 1. 시계열 데이터에서 AI 답변까지

시계열 데이터는 시간 정보에 따라 변화를 살펴보는 데이터입니다. 김실장의 한 행은 특정 날짜에 작업을 한 번 수행한 기록이고, `value`는 그 작업에 걸린 시간(분)입니다. 하루에 여러 작업을 기록할 수 있으므로 150건이 150일을 뜻하지 않습니다.

파이썬이 원본 기록의 기간·개수·평균·최대·최소·분야별 시간·반복 작업·최근 추세를 계산합니다. 결과를 Firestore에 요약으로 저장하고 화면과 상담이 함께 사용합니다. 최신 원본의 버전과 요약의 버전이 같으면 요약을 재사용하고, 기록이 바뀌면 다시 계산합니다.

김실장의 기본 가상 기록은 56일 동안 150건·6,524분입니다. 최근 7일 868분과 이전 7일 921분을 비교한 변화율은 `(868-921)/921×100 ≈ -5.75%`입니다. 이 결과는 기록된 시간의 감소이며, 효율이 좋아졌다는 증거는 아닙니다. 기록이 없는 날도 0분 근무나 휴식으로 단정하지 않습니다.

**스스로 설명하기:** 같은 날짜의 작업 세 건도 시계열 데이터인가요? 기록 한 건을 수정하면 다음 상담의 근거는 어떻게 바뀌나요?

<details>
<summary>설명에 들어갈 핵심</summary>

각 기록에 수행 날짜가 있고 날짜순으로 집계·비교할 수 있으므로 시계열 분석이 가능합니다. 수정하면 원본 버전이 증가하고 요약이 갱신됩니다. 다음 상담은 최신 요약을 사용하며, 과거 답변에는 당시 근거 버전을 보존합니다.

</details>

## 2. FastAPI에서 라우터와 서비스를 나눈 이유

API는 프로그램끼리 정해진 방식으로 요청·응답하는 접점이고, FastAPI는 Python으로 그 접점을 만드는 도구입니다.

김실장에서 **라우터**는 `/api/data` 같은 주소와 GET·POST 같은 요청 방식을 연결합니다. **서비스**는 기록 저장 뒤 요약을 갱신하거나, 요약과 질문을 묶어 GPT를 호출하는 업무 흐름을 처리합니다. **저장소 어댑터**는 Firestore 읽기·쓰기 방식을 담당하고, **스키마**는 데이터 형식과 검증 규칙을 정의합니다.

이렇게 나누면 같은 분석 서비스를 요약 API와 채팅에서 재사용할 수 있고, 테스트에서는 Firestore·GPT 연결을 대역으로 바꿀 수 있습니다. 라우터마다 분석과 저장 코드를 복사할 필요도 줄어듭니다.

**스스로 설명하기:** `POST /api/data`를 받는 코드와 평균 작업 시간을 계산하는 코드는 왜 다른 파일에 있나요?

<details>
<summary>설명에 들어갈 핵심</summary>

HTTP 주소·요청·응답을 처리하는 책임과 계산·저장 순서를 결정하는 책임이 다릅니다. 라우터는 서비스에 처리를 맡기고, 서비스는 분석 함수와 저장소를 사용합니다.

</details>

## 3. Pydantic 요청 검증

Pydantic은 요청이 정해진 데이터 형식과 규칙에 맞는지 검사합니다. 김실장은 유효한 날짜, 오늘 이후가 아닌 작업 날짜, 정수 1~1,440분, 필수 작업명, 허용 분야와 메모 길이를 검사합니다. 음수·소수·숫자로 된 문자열을 시간으로 조용히 바꾸지 않고, 정의하지 않은 필드도 거절합니다.

잘못된 값은 FastAPI의 요청 처리 단계에서 `422`로 안내합니다. 그래서 잘못된 시간 값이 DB에 저장되어 통계를 망가뜨리거나, 불필요한 GPT 호출로 이어지는 일을 줄입니다. 여러 기록을 읽어야 알 수 있는 하루 합계 1,440분 한도는 Firestore 트랜잭션 안에서 별도로 검사합니다.

**스스로 설명하기:** 실제 시간으로 `-10`, `1.5`, `"30"`을 보내면 어떻게 되나요? 화면에서 검사했는데 서버에서도 검사하는 이유는 무엇인가요?

<details>
<summary>설명에 들어갈 핵심</summary>

셋 다 현재 요청 모델에서 허용하지 않아 422가 됩니다. 화면을 거치지 않고 API를 직접 호출할 수 있으므로 서버 검증이 필요합니다. 화면은 입력 편의를, 서버는 저장과 처리의 일관성을 지킵니다.

</details>

구현: [공통 검증](../app/schemas/common.py), [작업 기록 모델](../app/schemas/records.py), [상담 조건 모델](../app/schemas/conversations.py).

## 4. Firestore 저장과 CRUD

Firestore는 문서를 컬렉션에 저장하는 데이터베이스입니다. 김실장은 `data`에 작업 기록, `conversations`에 상담과 메시지, `summaries`에 요약, `metadata`에 기록 버전과 요약 갱신 상태를 저장합니다.

| CRUD | 뜻 | 김실장 예시 |
| --- | --- | --- |
| Create | 만들기 | `POST /api/data`로 작업 기록 추가 |
| Read | 읽기 | `GET /api/data`로 목록 조회 |
| Update | 고치기 | `PUT /api/data/{id}`로 특정 기록 전체 수정 |
| Delete | 지우기 | `DELETE /api/data/{id}`로 특정 기록 삭제 |

`id`는 수정·삭제할 대상을 구분합니다. 기록 변경과 버전 증가는 하나의 트랜잭션으로 처리합니다. 대화도 질문·답변 한 쌍을 함께 저장하여 저장 실패 때 질문만 남는 일을 막습니다. 서버를 다시 실행해도 Firestore에 저장된 기록과 대화는 유지됩니다.

**스스로 설명하기:** 같은 이름의 작업이 여러 개라면 무엇으로 수정 대상을 구분하나요? 저장소가 서버 메모리뿐이면 재시작 때 어떤 문제가 있나요?

<details>
<summary>설명에 들어갈 핵심</summary>

각 문서의 고유 ID로 대상을 구분합니다. 메모리에만 저장하면 프로세스가 끝날 때 데이터가 사라지지만 Firestore의 문서는 계속 남습니다.

</details>

구현: [Firestore 기록 어댑터](../app/repositories/firestore_records.py), [대화 어댑터](../app/repositories/firestore_conversations.py).

## 5. 컨텍스트 주입

GPT가 DB를 저절로 아는 것은 아닙니다. 서버가 최신 데이터 요약을 조회해 시스템 프롬프트의 `RECORD_SUMMARY` 부분에 붙이고, 질문·현재 목표·시간·할 일·이전 대화를 함께 보냅니다. 이것이 이 프로젝트의 컨텍스트 주입입니다.

예를 들어 “지금 저장된 총 작업 시간이 얼마야?”라는 질문에 답할 수 있는 이유는, 이번 요청에 150건·6,524분이라는 요약을 함께 제공했기 때문입니다. 모델을 다시 학습시킨 것이 아니며, 새 요청마다 필요한 정보를 전달합니다. 원본 메모 전체를 보내지는 않습니다.

채팅은 `/api/data/summary`와 같은 요약 서비스를 직접 사용합니다. 서버가 자기 API를 HTTP로 다시 호출하는 구조는 아닙니다. GPT 결과는 형식·시간 합계·작업 누락·선행 관계 등을 검사한 뒤 저장하며, 일반 설명 문장의 모든 사실을 자동으로 보증하는 검증기는 아닙니다.

**스스로 설명하기:** 프롬프트에 요약을 넣는 것과 모델을 재학습하는 것은 어떻게 다른가요? 기록이 바뀌면 무엇을 새로 보내야 하나요?

<details>
<summary>설명에 들어갈 핵심</summary>

컨텍스트 주입은 이번 응답의 참고 정보를 추가하는 것이고 모델 가중치를 바꾸지 않습니다. 다음 요청에는 변경된 원본에 맞는 최신 요약을 보내야 합니다.

</details>

구현: [프롬프트 구성](../app/services/chat_prompt.py), [GPT 호출·검증·저장 흐름](../app/services/chat.py).

## 6. CORS·환경변수·키 관리

| 항목 | 필요한 이유 | 김실장의 적용 |
| --- | --- | --- |
| CORS | 다른 출처의 웹 화면이 API 응답을 읽도록 브라우저에 허용 범위를 알려 줌 | Vercel 웹 주소를 Render의 `ALLOWED_ORIGINS`에 지정 |
| 환경변수 | 로컬·배포 환경의 주소와 설정을 코드 수정 없이 구분 | 백엔드는 `.env` 또는 플랫폼 설정, 프론트는 빌드 시 공개 주소 반영 |
| 키 관리 | GPT 이용 권한·Firestore 접근 권한이 공개되는 것을 막음 | API 키와 서비스 계정 JSON은 백엔드에만 보관, Git과 프론트에서 제외 |

프론트의 `API_BASE_URL`은 공개해도 되는 서버 주소입니다. 반면 `OPENAI_API_KEY`와 서비스 계정 JSON은 비밀값입니다. `.env`라는 파일 이름만으로 안전해지는 것은 아니므로 `.gitignore`, 백엔드 전용 설정과 배포 파일 제외를 함께 적용합니다.

CORS는 로그인 기능이 아닙니다. 브라우저 외부의 직접 API 호출을 막지 못합니다. 현재 앱은 공개 가상 데이터 시연용이고, 실제 개인 데이터를 운영하려면 인증과 사용자별 접근 제어가 필요합니다.

**스스로 설명하기:** Vercel의 `API_BASE_URL`은 공개해도 되지만 API 키는 넣으면 안 되는 이유는 무엇인가요? CORS만 있으면 개인 데이터가 보호되나요?

<details>
<summary>설명에 들어갈 핵심</summary>

API 주소는 접속 위치이고 키는 사용·접근 권한입니다. 프론트 파일은 사용자 브라우저로 전달되므로 키가 들어가면 읽을 수 있습니다. CORS는 브라우저 정책이므로 개인 데이터 보호를 위한 인증을 대신하지 못합니다.

</details>
