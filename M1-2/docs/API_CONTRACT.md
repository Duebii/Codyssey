# 김실장 · 1단계 데이터와 API 계약

상태: **설계 v1 · 기록 CRUD·시계열 요약·대화 저장/불러오기·7단계 GPT 상담 구현·실제 외부 검증 완료**. 원본 150건과 요약을 유지하며 코디세이 제공 키로 실제 상담·계획 조정·자동 저장을 확인했습니다. 범위는 [로컬 서버 안내](BACKEND_START.md), [요약 안내](SUMMARY.md), [대화 기록 안내](CONVERSATIONS.md), [상담 안내](CHAT.md)를 참고합니다.

화면과 상담의 목적은 [화면 및 상담 설계](PRODUCT_SPEC.md)를 따릅니다. 이 문서는 요청 검증, 응답 형태와 분석 기준을 정합니다.

## 1. 공통 원칙

- API는 `/api` 아래에 두고 JSON을 사용합니다. 삭제 성공 응답은 본문 없이 `204`입니다.
- 작업 날짜와 상담의 오늘·내일 해석은 `Asia/Seoul` 기준입니다. 생성·수정 시각은 UTC ISO 8601 문자열로 저장합니다.
- 첫 버전의 데이터 출처는 `synthetic`으로 고정합니다. 브라우저에서 실제 데이터로 출처를 바꿀 수 없습니다.
- 원본 기록은 완료한 작업, 상담 조건은 앞으로 할 계획입니다. 채팅만으로 원본 기록을 추가하지 않습니다.
- 문자열은 앞뒤 공백을 정리하고, 숫자 필드는 정수만 받습니다. 숫자 문자열·소수·불리언을 시간으로 자동 변환하지 않습니다.
- 요청의 미정의 필드는 검증 오류로 처리합니다. 서버 관리 필드는 클라이언트가 수정하지 못하게 합니다.
- 목록은 페이지 단위로 제공하지만 분석은 현재 출처의 **전체 기록**을 대상으로 합니다.
- 아래 길이·개수 제한은 첫 버전의 구현 기준이며 실제 테스트 후 변경 시 문서도 갱신합니다.

## 2. 작업 기록 모델

### 추가·수정 요청

| 필드 | 필수 | 검증 |
| --- | --- | --- |
| `date` | 예 | 유효한 `YYYY-MM-DD`. 한국 기준 오늘 이후의 계획 날짜는 허용하지 않음 |
| `value` | 예 | 정수 1~1,440분 |
| `memo` | 예 | 0~2,000자. 빈 문자열 허용 |
| `task_name` | 예 | 공백 정리 후 1~80자 |
| `category` | 예 | `프리랜서`, `취업`, `창업` 중 하나 |
| `estimated_minutes` | 아니요 | `null` 또는 정수 1~1,440분. 생략 시 `null` |

`PUT`은 위 필드의 전체 교체입니다. 필수 필드는 모두 보내고, 예상 시간을 비우면 `null`로 저장합니다. 하루 여러 작업의 소요 시간 합계가 1,440분을 초과하면 거부합니다. 수정 시 해당 기록을 제외한 기존 합계와 새 값을 더해 확인합니다.

### 서버 관리 필드

| 필드 | 정의 |
| --- | --- |
| `id` | 새 기록은 서버가 생성. 더미 가져오기에서는 기존 `demo-001` 형식의 ID 사용 |
| `source` | 첫 버전은 `synthetic` |
| `created_at` | 최초 저장 시각. 수정해도 유지 |
| `updated_at` | 마지막 변경 시각 |

기존 JSON은 가져오기용 원본입니다. 가져올 때 기록 검증을 수행하고 생성·수정 시각을 부여합니다. 가져오기 재실행은 기존 ID를 확인해 중복 추가를 피하며, 사용자 수정 기록을 조용히 덮어쓰지 않습니다.

### 필수 데이터 API

| 메서드·주소 | 요청 | 성공 응답 |
| --- | --- | --- |
| `POST /api/data` | 추가 요청 | `201`, `{ "item": 기록 }` |
| `GET /api/data` | `page` 기본 1, `page_size` 기본 50·최대 100 | `200`, `{ "items": [...], "total": 전체 건수, "page": 페이지, "page_size": 크기, "source": "synthetic" }` |
| `PUT /api/data/{id}` | 전체 수정 요청 | `200`, `{ "item": 수정된 기록 }` |
| `DELETE /api/data/{id}` | 없음 | `204`, 본문 없음 |
| `GET /api/data/summary` | 없음 | `200`, 최신 요약과 근거 메타데이터 |

목록 정렬은 `date` 내림차순, 같은 날짜는 `id` 오름차순입니다. 없는 ID 수정·삭제는 `404`입니다. 화면에 표시한 기록 한 건을 수정·삭제하므로 `GET /api/data/{id}`는 첫 버전 필수 API에 추가하지 않습니다.

## 3. 요약 계산과 저장

요약은 [로컬 분석 예시](../data/summary.preview.json)의 지표와 아래 정의를 기준으로 구현합니다. 현재 파일은 계산 예시이며 API 실행 결과가 아닙니다.

| 항목 | 계산·해석 |
| --- | --- |
| 기간·기준일 | 전체 기록의 최소·최대 날짜. `as_of`는 최대 날짜 |
| 개수 | 현재 출처의 전체 기록 수. 페이지 크기와 무관 |
| 총 시간 | `value` 합계 |
| 건당 평균·최대·최소 | 기록 한 건의 소요 시간을 기준으로 계산 |
| 기록일 평균 | 총 시간 ÷ 기록이 존재하는 날짜 수 |
| 일별 시간 | 그 날짜의 합계. 기록이 없으면 `null`과 `unrecorded` |
| 7일 구간 | 최소 날짜부터 연속 7일씩 집계. 마지막 구간이 7일 미만이면 화면에 부분 기간 표시 |
| 분야별 비중 | 해당 분야의 시간 ÷ 전체 시간 × 100 |
| 작업별 통계 | 같은 `category` 안에서 `task_name`을 공백 정리 후 정확히 일치하는 이름으로 묶음 |
| 반복 업무 후보 | 3회 이상 기록된 작업을 누적 시간 내림차순으로 표시. 자동화 확정 의미 없음 |

평균·퍼센트는 소수점 둘째 자리, 실제/예상 비율은 셋째 자리까지 표시합니다. 방향 판정은 반올림 전 값으로 하고, 시간 합계는 정수로 유지합니다. 분야별 반올림 비중의 합이 정확히 100이 아닐 수 있습니다.

### 예상 시간과의 비교

`estimated_minutes`가 있는 기록끼리만 비교합니다. 같은 작업의 전체 건수·총 시간과, 비교 가능한 기록의 건수(`paired_count`)·실제 시간 합계·예상 시간 합계를 구분합니다.

- 평균 초과 시간 = 비교 가능한 기록의 `(실제 - 예상)` 합계 ÷ 비교 가능한 건수.
- 실제/예상 비율 = 비교 가능한 기록의 실제 합계 ÷ 예상 합계.
- 예상 시간이 없는 기록은 초과 시간의 분자와 분모에서 제외합니다.
- 비교 가능한 기록이 없으면 비교 지표는 `null`입니다.

현재 더미 150건에는 예상 시간이 모두 있어 기존 예시의 수치를 유지할 수 있습니다. 위 비교 건수 등 추가 필드는 실제 API 구현 시 포함합니다.

### 최근 추세

마지막 기록일 `D`를 기준으로 최근 구간 `D-6 ~ D`와 이전 구간 `D-13 ~ D-7`의 기록된 총 시간을 비교합니다. 현재 데이터에서는 각각 2026-10-14~20, 2026-10-07~13입니다.

- 변화율 = `(최근 합계 - 이전 합계) ÷ 이전 합계 × 100`.
- 5% 초과는 `increase`, -5% 미만은 `decrease`, 나머지는 `stable`.
- 전체 기록 기간이 14일 미만이거나, 어느 구간에 기록이 없거나, 이전 합계가 0이면 `insufficient_data`와 변화율 `null`.
- 두 구간의 기록 개수·기록일 수도 함께 표시합니다. 근무량·성과·효율의 변화로 단정하지 않습니다.
- 기준일은 오늘이 아닌 마지막 기록일임을 화면과 AI 답변의 근거에 표시합니다.

### 빈 데이터

빈 데이터의 요약은 정상 `200`입니다. 개수·총 시간·기록일 수는 0, 기간·기준일·평균·최대·최소·변화율은 `null`, 목록 지표는 빈 배열, 추세는 `insufficient_data`입니다. 기록일 평균의 분모가 0일 때 나눗셈을 하지 않습니다.

### 저장과 최신성

- `data`: 원본 기록, `summaries/synthetic`: 현재 출처의 요약, `conversations`: 대화와 상담 조건.
- 데이터 변경마다 서버가 관리하는 기록 버전 `data_revision`을 갱신합니다. 요약에도 계산 대상 버전과 생성 시각을 저장합니다.
- 요약 API는 `{ "summary": 분석 결과, "data_revision": 버전, "generated_at": 생성 시각 }` 형태로 반환합니다.
- 변경 후 요약 갱신을 시도합니다. 추가·수정 응답은 `{ "item": 기록, "warning": null 또는 경고 객체 }`입니다. 원본 변경은 성공했으나 요약만 실패하면 `warning`에 `code: summary_refresh_failed`와 재조회 안내 `message`를 표시합니다. 삭제 `204` 후에는 화면이 요약을 다시 조회합니다.
- 조회 시 원본과 요약의 버전이 다르면 최신 원본으로 다시 계산합니다. 재계산할 수 없으면 `503`으로 안내하고 오래된 요약을 최신처럼 반환하지 않습니다.
- 채팅도 같은 요약 서비스를 사용합니다. 요약 조회 실패를 빈 기록으로 바꾸지 않습니다.

5단계에서 요약 계산·갱신·최신성 응답을 구현했습니다. 원본과 버전을 같은 트랜잭션 스냅샷으로 읽고, 저장 시 버전이 달라졌으면 최대 3회 재계산합니다. 최신성 확인에 실패하면 `503 summary_unavailable`입니다. 내부 캐시 스키마 버전은 1이며 일별 분석 기간은 최대 3,660일, 요약 JSON은 UTF-8 기준 900,000바이트로 제한합니다. 원본 직접 수정으로 앱의 버전 규칙을 우회하는 방식은 지원하지 않습니다.

현재 `summary.preview.json`에는 실행 시각·저장소 버전과 일부 확장 필드가 없습니다. 원본 더미데이터와 로컬 예시는 이 설계 작업에서 수정하지 않습니다.

## 4. 상담 조건 모델

| 필드 | 검증·의미 |
| --- | --- |
| `goal` | `null` 또는 최대 500자 |
| `available_minutes` | `null` 또는 정수 1~1,440분 |
| `tasks` | 최대 10개. 아래 작업 조건 구조 사용 |
| `constraints` | `null` 또는 최대 1,000자 |

작업 조건 한 건은 다음과 같습니다.

| 필드 | 검증·의미 |
| --- | --- |
| `id` | 상담 안에서 고유한 1~40자 영문·숫자·`_`·`-` ID |
| `title` | 1~100자 |
| `due_date` | `null` 또는 유효한 `YYYY-MM-DD`. 지난 마감도 입력 가능하며 지난 사실을 설명 |
| `importance` | `high`, `medium`, `low`, `unknown`. 기본 `unknown` |
| `depends_on` | 다른 작업의 ID 배열. 중복·없는 ID·자기 참조·순환 금지 |

날짜만 입력한 마감은 정확한 시각이 미정인 것으로 해석합니다. 시각이 순서에 영향을 주면 확인합니다. 자연어의 할 일은 확인된 정보만 조건에 반영하고 중요한 추측을 확정된 입력으로 저장하지 않습니다.

이전 상담에서 조건을 이어받습니다. `context` 전체가 생략되거나 `null`이면 기존 조건을 유지합니다. 객체 안에 포함된 조건 필드는 기존 값을 대체하고, 생략한 필드는 유지합니다. `goal`·`available_minutes`·`constraints`의 `null`은 해당 값을 지우는 뜻이고, `tasks: []`는 할 일 목록을 비우는 뜻입니다. `tasks`를 보내면 목록 전체를 교체합니다. 새 상담의 기본값은 목표·가능 시간·제약이 `null`, 할 일이 빈 배열입니다. UI는 보내기 전 최신 조건 전체를 확인할 수 있게 합니다.

자연어에서 명시적으로 제공한 작업·시간·마감도 검증된 상담 조건에 반영하고 화면에 보여줍니다. 자연어로 새로 파악한 작업에는 상담 안에서 사용할 ID를 부여합니다. 값이 모호하거나 구조화 입력과 충돌하면 질문으로 확인한 뒤 변경합니다.

## 5. 채팅 API

### `POST /api/chat`

| 요청 필드 | 규칙 |
| --- | --- |
| `message` | 필수, 공백 정리 후 1~4,000자 |
| `conversation_id` | 생략 또는 `null`이면 새 상담, 기존 ID면 이어서 상담 |
| `mode` | `strategy`, `automation`, `review`. 첫 상담의 기본은 `strategy`, 기존 상담에서 생략하면 직전 모드 유지 |
| `context` | 선택. 위 상담 조건을 갱신할 필드 |

예시 요청입니다. 마감과 가능 시간은 가상 상담 입력이며 더미 기록에서 추론한 사실이 아닙니다.

```json
{
  "message": "지원서와 포트폴리오 중 무엇부터 어떻게 할까요?",
  "conversation_id": null,
  "mode": "strategy",
  "context": {
    "goal": "마감 전에 지원서 초안 완성",
    "available_minutes": 120,
    "tasks": [
      {"id": "t1", "title": "지원서 작성", "due_date": "2026-10-22", "importance": "high", "depends_on": []},
      {"id": "t2", "title": "포트폴리오 문구 수정", "due_date": null, "importance": "medium", "depends_on": []}
    ],
    "constraints": "이번에는 지원서 초안까지 작성"
  }
}
```

### 성공 응답과 메시지

성공은 `200`이며 `{ "conversation_id": ID, "message": 저장된 비서 메시지, "context": 최신 상담 조건 }`를 반환합니다. 사용자·비서 메시지가 저장된 뒤 성공으로 처리합니다. 실패 시 자동으로 재호출해 중복 과금·저장을 일으키지 않습니다.

비서 메시지의 필드는 다음과 같습니다.

| 필드 | 정의 |
| --- | --- |
| `id`, `role`, `created_at` | 메시지 식별자, `assistant`, 생성 시각 |
| `content` | 화면에 표시할 안전한 텍스트. 계획이 있으면 같은 구조화된 계획에서 설명을 구성 |
| `mode` | 해당 응답의 상담 종류 |
| `reply_type` | `clarification`, `advice`, `plan`, `automation`, `review` 중 하나 |
| `plan` | 확정된 시간 배분이 있는 실행 전략, 그 외에는 `null` |
| `evidence` | 출처, 데이터 기간, 기준일, 개수, 원본 버전. 당시 근거를 메시지와 함께 보관 |

일정 확정에 필요한 정보가 없으면 `clarification`으로 질문합니다. 시간표 없이 우선순위나 첫 행동을 안내하면 `advice`를 사용합니다. 입력 오류, 요약 실패, AI 오류는 확인 질문이나 정상 답변으로 위장하지 않습니다.

### 실행 전략 구조와 검증

`plan`은 다음 형태입니다. 예시는 계획 자체의 구조를 설명하며 실제 AI 응답이 아닙니다.

```json
{
  "available_minutes": 120,
  "tasks": [
    {
      "task_id": "t1",
      "priority": 1,
      "reason": "사용자가 가까운 마감과 높은 중요도를 입력했습니다.",
      "completion_criteria": "지원 동기와 관련 경험을 포함한 초안 저장",
      "steps": [
        {"action": "공고 요구 사항과 사용할 경험 확인", "minutes": 10},
        {"action": "지원 동기와 경험 초안 작성", "minutes": 60},
        {"action": "빠진 항목 확인과 초안 저장", "minutes": 25}
      ],
      "first_action": "공고를 열고 요구 역량 세 가지 적기",
      "checkpoint": "70분 경과 시 주요 문단이 작성됐는지 확인",
      "fallback": "초안이 밀리면 문장 다듬기를 줄이고 필수 항목을 먼저 채우기"
    }
  ],
  "buffer_minutes": 25,
  "deferred": [{"task_id": "t2", "reason": "이번 가능 시간은 지원서 초안에 우선 배정"}],
  "assumptions": ["이번 범위는 제출 완료가 아닌 초안 작성"]
}
```

서버는 구조와 함께 다음을 검증합니다.

- 가능 시간은 최신 상담 조건의 확인된 값과 같아야 합니다.
- 작업·미룰 작업의 ID는 현재 상담 조건에 존재해야 하며, 계획과 미루기 양쪽에 중복 배치하지 않습니다.
- 단계별 시간은 양의 정수, 완충 시간은 0 이상의 정수입니다.
- 모든 단계 시간과 완충 시간의 합은 가능 시간 이하여야 합니다. 위 예시는 `10 + 60 + 25 + 25 = 120`분입니다.
- 선행 작업을 해결하지 않고 후속 작업을 완료할 수 있다고 계획하지 않습니다.
- 완료 기준·첫 행동·점검·대안과 우선순위 이유가 있어야 합니다.

AI 출력이 구조나 시간 예산을 위반하면 제한된 수정 절차를 거칩니다. 수정에도 실패하면 오류로 안내하고 검증되지 않은 계획을 정상 답변으로 저장·표시하지 않습니다. 모델의 자유 텍스트만 믿고 시간 합계를 판단하지 않습니다.

## 6. 대화 저장 API

| 메서드·주소 | 요청·동작 | 성공 응답 |
| --- | --- | --- |
| `POST /api/conversations` | 제목, 선택 모드·조건으로 빈 상담 생성 | `201`, `{ "conversation": 상세 대화 }` |
| `GET /api/conversations` | `page` 기본 1, `page_size` 기본 20·최대 50 | `200`, `{ "items": 목록, "total": 전체 수, "page": 페이지, "page_size": 크기 }` |
| `GET /api/conversations/{id}` | 전체 메시지와 최신 조건 조회 | `200`, `{ "conversation": 상세 대화 }` |
| `DELETE /api/conversations/{id}` | 해당 대화만 삭제 | `204`, 본문 없음 |

`POST`는 새 상담의 저장에 사용합니다. 제목 생략 시 `새 상담`으로 만들고, 최초 질문이 저장될 때 질문 앞부분을 최대 40자로 잘라 제목으로 사용합니다. 사용자가 지정한 제목은 유지합니다. 모드 기본값은 `strategy`, 조건 기본값은 위 상담 조건 모델과 같습니다. 메시지 쌍의 자동 저장은 `/api/chat`이 담당하며, 두 API에서 같은 메시지를 중복 저장하지 않습니다.

- 대화: ID, 제목(1~80자), 출처, 생성·갱신 시각, 최신 모드·조건, 메시지 배열, 저장 충돌 검사용 `revision`.
- 목록: ID, 제목, 갱신 시각, 메시지 수, 마지막 메시지 미리보기(최대 100자). **전체 `messages`는 포함하지 않습니다.**
- 목록 정렬: 갱신 시각 내림차순, 같은 시각은 ID 오름차순.
- 상세 조회: 전체 메시지, 최신 조건, 각 비서 답변 당시의 분석 근거를 포함합니다.
- 사용자 메시지는 `user`, 비서 메시지는 `assistant`입니다. 클라이언트가 `system` 지시문을 저장하거나 바꿀 수 없습니다.
- 메시지 저장 시 모드·질문 당시 조건을 함께 보관해 상담 흐름을 설명할 수 있게 합니다.
- 대화 불러오기 자체는 GPT를 호출하지 않습니다. 새 질문을 전송할 때 최신 요약과 기존 대화를 사용합니다.
- 첫 버전은 대화당 최대 100개 메시지, 메시지 내용 총 60,000자, 직렬화된 전체 대화 최대 500KiB로 제한합니다. 먼저 도달한 제한을 적용하고 새 상담 시작을 안내합니다.
- 실제 GPT에 전달할 대화는 최근 최대 12개 메시지·본문 합계 20,000자 이내와 최신 조건으로 제한합니다. 저장한 전체 이력과 모델에 전달한 범위를 구분해 안내합니다.
- 원본 메모·사용자 메시지는 참고 데이터이며 시스템 규칙을 바꾸는 지시로 취급하지 않습니다.

6단계에서 네 개의 공개 API와 내부 `save_turn()`을 구현했습니다. 사용자·비서 한 쌍과 조건·미리보기를 같은 문서 트랜잭션으로 저장하고 대화 버전을 1 올립니다. 저장 직전에 원래 버전이 바뀌었으면 `409 conversation_conflict`, 삭제됐으면 `404`이며 자동으로 새 상담을 만들지 않습니다. 내부 메시지 입력은 공개 `POST` 요청에 포함하지 않습니다. 7단계는 GPT 생성·검증 후 기존 상담에는 `save_turn()`, 새 상담에는 질문·답변을 포함한 문서 생성을 연결했습니다. 자세한 제한·오류·현재 실제 검증 상태는 [상담 안내](CHAT.md)에 정리했습니다.

## 7. 오류와 화면 대응

검증 오류도 같은 형식을 사용하도록 후속 구현에서 예외 처리를 구성합니다.

```json
{
  "error": {
    "code": "invalid_request",
    "message": "가능 시간은 1~1440 사이의 정수로 입력해 주세요.",
    "fields": ["context.available_minutes"]
  }
}
```

| 상태 | 예시 코드·의미 | 화면 처리 |
| --- | --- | --- |
| `422` | `invalid_request` | 해당 입력에 오류 표시, 입력 유지 |
| `404` | `not_found` | 삭제됐거나 없는 대화·기록 안내 후 목록 새로고침 |
| `409` | `conversation_limit`, `conversation_conflict`, `record_conflict` | 대화 한도·동시 변경 또는 기록 ID·출처 충돌 안내 |
| `422` | `daily_limit_exceeded` | 해당 날짜의 총 시간과 새 기록 확인 안내 |
| `413` | `payload_too_large` | 입력·대화 크기 줄이기 안내 |
| `429` | `rate_limited` | 요청 제한과 재시도 안내 |
| `502` | `ai_response_invalid`, `ai_unavailable` | 정상 계획처럼 표시하지 않고 재시도 안내 |
| `503` | `storage_unavailable`, `summary_unavailable` | 저장·근거 조회 실패 구분, 입력 유지 |
| `504` | `upstream_timeout` | 응답 지연 안내. 자동 반복 호출하지 않음 |

예외 응답과 로그에 키·인증 JSON·원본 외부 서비스 오류 전문을 노출하지 않습니다. 완료 여부가 불명확한 요청은 목록이나 대화를 다시 조회해 상태를 확인한 뒤 재시도하도록 안내합니다.
