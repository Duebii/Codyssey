# 김실장 더미데이터 설명

**제출 허용 확인:** 2026-10-28 사용자가 과제 담당자에게 더미데이터 제출 허용을 확인받았다고 알려 주었습니다. 별도의 담당자 공문을 직접 검토한 것은 아니며, 사용자 확인을 근거로 기록합니다. 이 확인은 제출 허용에 관한 것으로 데이터가 실제 관측값이라는 뜻은 아닙니다.

## 1. 데이터의 성격

이 데이터는 프리랜서·취업 준비·창업 준비를 병행하는 **가상 사용자 한 명**의 작업 수행 기록입니다. 실제 사용자의 생활, 생산성, 사업 성과를 나타내지 않습니다.

분석할 수 있는 패턴을 의도적으로 넣었으며, 그 패턴을 발견했다고 해서 AI의 분석 능력이나 실제 효과가 검증된 것은 아닙니다. 목적은 기록 관리, 분석, 컨텍스트 주입, 데이터 기반 답변의 흐름을 개발하고 시연하는 것입니다.

모든 기록에 `source: "synthetic"`과 `시연용:`으로 시작하는 메모를 포함합니다. 실제 기록을 도입할 때는 데이터 출처별로 구분하고 요약도 분리해야 합니다.

## 2. 기록 한 건의 의미

**작업을 한 번 수행한 내역**을 한 건으로 봅니다. 날짜가 같아도 별도의 작업 수행이면 별도의 기록입니다. 같은 자료 취합 작업을 다음 날 수행한 기록도 새로운 한 건입니다.

2026-08-26부터 2026-10-20까지 8주 중 평일 40일에 하루 3~4건을 배치해 총 150건을 만들었습니다. 데이터의 양을 늘리기 위한 동일 행 복제는 하지 않습니다.

## 3. 필드 정의

| 필드 | 자료형 | 의미·규칙 |
| --- | --- | --- |
| `id` | 문자열 | `demo-001` 형식의 고유 식별자. 이후 API에서 새로 만들 ID와 구분 |
| `date` | 문자열 | 작업 수행 날짜, 한국 기준 `YYYY-MM-DD` |
| `value` | 정수 | 소요 시간, 분. 현재 더미데이터는 1~1,440 범위 |
| `memo` | 문자열 | 작업 방식, 사용 도구, 사람의 판단이 필요한 단계 등 가상의 맥락 |
| `task_name` | 문자열 | 반복 작업을 묶을 이름. 예: 자료 취합, 제안서 작성 |
| `category` | 문자열 | 프리랜서·취업·창업 중 하나 |
| `estimated_minutes` | 정수 | 작업 전에 예상한 시간이라는 가상 설정. 단위는 분 |
| `source` | 문자열 | 현재 파일은 모두 `synthetic` |

과제의 기본 형태인 `(date, value, memo)`를 유지하고, 업무 분석에 필요한 필드를 추가했습니다. 앱 구현 시 이 정의를 기준으로 Pydantic 요청 모델을 설계하되, `id`와 출처는 서버에서 관리하는 방향으로 구분합니다.

## 4. 의도적으로 넣은 가상 패턴

### 자료 취합의 시간 부담 증가

자료 취합은 평일마다 등장하며 총 40회입니다. 이메일과 공유 폴더의 내용을 스프레드시트에 옮기는 가상의 반복 작업으로 설정했습니다.

첫 7일 구간 합계는 **99분**, 마지막 7일 구간 합계는 **237분**입니다. 두 구간 모두 5회이므로 수행 횟수 변화와 소요 시간 증가를 구분해 살펴볼 수 있습니다.

자동화 상담에서는 자료 형식, 접근 권한, 예외 처리, 사람의 확인 단계 등을 추가로 묻도록 설계할 수 있습니다. 수치만으로 자동화 가능 여부를 확정하지 않습니다.

### 제안서 작성의 예상 시간 초과

제안서 작성은 총 20회이며, 예상 시간은 매회 40분으로 설정했습니다. 실제 소요 시간으로 설정한 값은 20회 모두 이를 초과합니다.

전략 상담에서 다음 제안서의 작업 시간을 넉넉히 배정하는 예시를 만들 수 있습니다. 초과 원인을 확정하려면 별도 정보가 필요합니다.

### 후반부의 취업 준비 비중 증가

전반 4주에 배치한 아이디어 검증 준비를 후반 4주에는 지원서 작성으로 전환했습니다.

전체 소요 시간 중 취업 분야의 비중은 전반 **21.71%**, 후반 **42.33%**입니다. 이는 가상의 시간 배분 변화이며, 실제로 취업을 최우선 목표로 선택했다는 뜻은 아닙니다.

## 5. 분석 예시의 계산 기준

`summary.preview.json`에는 다음을 담습니다.

- 전체 기간과 개수, 총 소요 시간
- 작업 한 건의 평균·최대·최소 소요 시간
- 기록이 존재하는 날짜의 일평균 소요 시간
- 분야별 기록 수·소요 시간·시간 비중
- 날짜별 합계와 미기록 여부
- 첫 날짜를 기준으로 묶은 동일 길이의 7일 구간별 합계
- 작업명별 수행 횟수·평균 시간·예상 대비 초과 시간
- 3회 이상 기록된 작업의 반복 업무 검토 목록

이번 데이터의 전체 소요 시간 합계는 **6,524분(108시간 44분)**입니다. 반복 업무 검토 목록은 자동화 확정 목록이 아닙니다.

### 최근 추세

- 기준일: 마지막 기록일인 **2026-10-20**
- 최근 구간: 2026-10-14 ~ 2026-10-20
- 비교 구간: 2026-10-07 ~ 2026-10-13
- 비교 대상: 두 구간의 **기록된 총 소요 시간**
- 방향: 5% 초과 증가, -5% 미만 감소, 그 사이 유지
- 비교할 기록이나 양의 기준값이 부족하면 `insufficient_data`

이 기준은 개발을 위한 정의입니다. 오늘 날짜에 따라 바뀌지 않으며, 전체 시간 변화만으로 효율이나 성과를 판정하지 않습니다. 1단계에서 확정한 실제 서비스의 검증·통계 기준은 [API 및 데이터 계약](API_CONTRACT.md)을 따릅니다. 기록 기간이 부족하거나 예상 시간이 누락된 경우의 처리 등은 실제 API 구현 시 추가하고, 현재 JSON은 원본 더미데이터의 로컬 분석 예시로 유지합니다.

### 미기록 처리

주말 16일은 기록이 없습니다. 일별 분석에서 `total_minutes: null`, `status: "unrecorded"`로 표시합니다. 이를 0분 작업이나 휴식으로 해석하지 않습니다. 기록이 있는 날짜의 일평균은 **40일**을 분모로 계산합니다.

## 6. 데이터만으로 알 수 없는 것

- 오늘의 목표와 중요도, 실제 마감일과 선행 작업
- 지금 사용할 수 있는 시간과 작업 제약
- 작업의 품질, 실제 제출·매출·취업 성과
- 자동화 허용 범위, 접근 권한과 사용 도구의 최신 기능
- 자동화 구축·유지 시간과 실제 절감 효과

우선순위와 실행 전략 상담에서는 이런 내용을 별도로 확인해야 합니다. 앞으로 할 계획과 이미 수행한 기록도 구분해 저장합니다.

## 7. 재현과 검증

생성 조건은 고정된 날짜 범위와 난수 시드 `1021`입니다. Python 표준 라이브러리만 사용합니다.

```powershell
python scripts/generate_dummy_data.py
python scripts/verify_dataset.py
python scripts/generate_dummy_data.py --check
```

독립 검증은 150건·고유 ID·날짜·단위·출처·하루 시간 합계·요약 일치·미기록 처리와 세 가지 가상 패턴을 확인합니다. `--check`는 파일을 수정하지 않고 같은 생성 조건의 결과와 일치하는지 검사합니다.
